Technische Beschreibung der GitHub-Actions-Workflows für Admins
(Freigabe, IP-Vergabe, VM-Erstellung) und Betreuer*innen des Repos.

[[grundprinzip]]
== Grundprinzip

GitHub startet bei jedem Ereignis im Repo alle Workflows, die auf dieses Ereignis hören.
Jeder Workflow prüft zuerst eine *Bedingung* (`if:`). Trifft sie nicht zu, wird er sofort
übersprungen („skipped"). Trifft sie zu, lädt er `.github/scripts/antrag.js` und führt ein
Skript aus.

IMPORTANT: Alle Bot-Aktionen (Labels, Kommentare, Titel) laufen mit dem `GITHUB_TOKEN`.
Änderungen mit diesem Token *lösen keine weiteren Workflows aus* — keine Endlosschleifen.
Setzt der Bot z.B. `status: neu`, reagiert kein anderer Workflow darauf.

[cols="2,2,3",options="header"]
|===
|Ereignis |Workflow |Bedingung

|Issue erstellt / bearbeitet
|`antrag-pruefen.yaml` („Antrag prüfen")
|Label `vm-antrag` und Issue offen

|Label hinzugefügt
|`status.yaml` („Status")
|Label `vm-antrag` und Label = `status: freigegeben`, `status: erstellt` oder `abgelehnt`

|Kommentar geschrieben
|`kommandos.yaml` („Kommandos")
|beginnt mit `/ip` oder `/ablehnen`, Label `vm-antrag`
|===

.Status-Kette
[source,text]
----
(Antrag) ──► ungültig ◄──► status: neu ──► status: freigegeben ──► status: ip-vergeben ──► status: erstellt
              Bot            Bot            Peter (Label)          Himmelbauer (/ip)        Wagner/Brückner (Label)

Jederzeit vor „erstellt":  /ablehnen <Begründung>  oder Label abgelehnt  ──► abgelehnt + Issue geschlossen
----

.Kommandos (nur Rolle Triage oder höher)
[cols="2,3",options="header"]
|===
|Kommando |Wirkung

|`/ip <adresse>` |IP eintragen, nur bei `status: freigegeben` (<<ip>>)
|`/ablehnen <Begründung>` |Antrag ablehnen und schließen (<<ablehnen>>)
|===

[[personen]]
=== Zuständige Personen

Die erwähnten Personen kommen aus Repo-Variablen. Ohne Variable gilt der Default im Workflow.

[cols="1,2,2",options="header"]
|===
|Variable |Aufgabe |Default

|`FREIGABE` |Freigabe des Antrags |`bauepete`
|`IP_VERGABE` |IP-Adresse eintragen |`htl-leonding` (Platzhalter für Thomas Himmelbauer)
|`VM_ERSTELLUNG` |VM in Proxmox anlegen („Mailverteiler") |`Master-Andi MWagnerOE5AOO`
|===

[source,bash]
----
gh variable set IP_VERGABE -R htl-leo-infra/vm-antraege --body <username>
----

[[antrag]]
== Schüler*in erstellt den Antrag

*Ereignis:* `issues: opened` → Workflow *Antrag prüfen*

. *Formular auslesen* — Der Issue-Body hat das Format `### Projektname` + Leerzeile + Wert.
  `parseBody()` übersetzt die deutschen bzw. englischen Überschriften in Feld-IDs
  (`projektname`, `internet`, …). `_No response_` gilt als leer.
. *Titel setzen* — `[VM] <projektname>` wird z.B. zu `[VM] notenrechner`.
. *Doppelte Namen suchen* — alle *offenen* Anträge (außer `abgelehnt`) laden und deren
  Projektnamen und DNS-Namen auslesen.
. *Prüfen:*
** *Fehler:* Teammitglieder leer oder kein gültiger Schul-Benutzername
   (`^(ad|kd|if|it|el|bg)\d{6}$`, z.B. `if123456`); Name ungültig (`^[a-z][a-z0-9-]{2,29}$`) oder bereits vergeben; DNS Name bereits
   von einem anderen offenen Antrag mit Internet „Yes" belegt; bei Internet
   „Yes" fehlen Ports oder DNS; Portnummer ungültig; DNS kein gültiger Hostname
** *Nur Warnung:* Port 22/3306/5432/6379/27017 öffentlich; Ports/DNS angegeben, obwohl
   Internet „No"
. *Mit Fehlern:* Label `ungültig`, Prüfkommentar mit allen Fehlern und unsichtbarer
  Markierung `<!-- vm-antrag:pruefung -->`. Ende — Peter wird *nicht* benachrichtigt.
. *Ohne Fehler:* Label `status: neu`, Kommentar `@bauepete Neuer VM-Antrag … bitte freigeben`
  und für die Schüler*innen „Danke, euer Antrag ist eingegangen".
  *GitHub schickt Peter eine Mail* (wegen der Erwähnung).

NOTE: Die Sprache richtet sich nach dem Label `english`, das das englische Formular
automatisch setzt. Texte an Schüler*innen sind dann englisch, Texte an Admins immer deutsch.

[[bearbeiten]]
== Schüler*in bearbeitet den Antrag

*Ereignis:* `issues: edited` → derselbe Workflow *Antrag prüfen*, derselbe Ablauf.

* *Immer noch fehlerhaft:* Der *vorhandene* Prüfkommentar wird aktualisiert (erkannt an der
  Markierung) — kein neuer Kommentar.
* *Jetzt korrekt:* Label `ungültig` weg, Prüfkommentar zeigt „✅ gültig". Ist noch kein
  Status-Label gesetzt: `status: neu` und Mail an Peter.
* *Bereits freigegeben und nachträglich bearbeitet* (Label `status: freigegeben`,
  `status: ip-vergeben` oder `status: erstellt`): Der Bot vergleicht alten und neuen Stand
  (`changes.body.from`) und postet an `FREIGABE` und `VM_ERSTELLUNG` eine Tabelle
  *Feld | vorher | nachher*. Bei geänderten Teammitgliedern zusätzlich
  „*Teammitglieder geändert → Proxmox-Zugriff prüfen!*". Danach wird normal neu geprüft;
  das Status-Label bleibt.

IMPORTANT: Die Teammitglieder (Schul-Benutzernamen) bekommen Zugriff auf die Proxmox-Oberfläche.
Eine Änderung nach der Freigabe muss deshalb immer geprüft werden.

[[freigabe]]
== Peter gibt frei

*Aktion:* Peter setzt das Label `status: freigegeben` (braucht Rolle Triage, d.h. Mitglied
im Team `vm-admins`).

*Ereignis:* `issues: labeled` → Workflow *Status* (Zweig `status: freigegeben`)

. Label `status: neu` entfernen.
. Kommentar: `@<IP_VERGABE> Antrag … wurde von @bauepete freigegeben. Bitte /ip 10.x.x.x/24 public x.x.x.x/24`
  und für die Schüler*innen „Euer Antrag wurde freigegeben".
. *Die Person für die IP-Vergabe bekommt eine Mail.*

NOTE: Der Workflow *Status* startet bei jedem Label, läuft aber nur bei `status: freigegeben`,
`status: erstellt` und `abgelehnt`. Alle anderen Labels werden übersprungen.

[[ip]]
== Himmelbauer trägt die IP ein

*Aktion:* Kommentar im Issue:

[source,text]
----
/ip 10.9.32.1/24
/ip 10.9.32.1/24 public 193.18.22.7/24
----

Präfix (`/24`) und öffentliche IP sind optional. Statt `public` geht auch `/public`.

*Ereignis:* `issue_comment: created` → Workflow *Kommandos* (Zweig `/ip`)

. *Berechtigung prüfen* — Rolle der kommentierenden Person im Repo abfragen. Unter Triage
  (z.B. Schüler*innen): nur Log-Eintrag, *kein sichtbarer Kommentar*.
. *Status prüfen* — Ohne Label `status: freigegeben`: 😕-Reaktion und Hinweis
  „/ip geht nur bei Label status: freigegeben".
. *IP prüfen* — Nur die erste Zeile zählt: interne IPv4 mit optionalem Präfix (≤ 32),
  optional `public <IPv4>[/Präfix]`. Sonst 😕 und Formathinweis.
. *Erfolg:*
** Label `status: freigegeben` → `status: ip-vergeben`
** 👍-Reaktion auf den Kommentar
** Kommentar `@MWagnerOE5AOO @Master-Andi Bitte VM anlegen …` mit *Tabelle aller Daten*
   und IP, für die Schüler*innen „IP-Adresse eurer VM: …"
** *Michael und Andreas bekommen eine Mail* mit dieser Zusammenfassung — das ist der
   „Mailverteiler".

[[erstellt]]
== VM wird angelegt

*Aktion:* VM in Proxmox anlegen (manuell), danach Label `status: erstellt` setzen.

*Ereignis:* `issues: labeled` → Workflow *Status* (Zweig `status: erstellt`)

. Alle vorherigen Status-Labels entfernen (`status: neu`, `status: freigegeben`,
  `status: ip-vergeben`) — auch wenn Schritte übersprungen wurden.
. Kommentar `@<antragsteller*in> 🎉 Eure VM … ist bereit. Zugangsdaten auf anderem Weg …`
. *Die Antragsteller*in bekommt eine Mail.*

WARNING: Zugangsdaten zur VM niemals im Issue posten — das Repo ist öffentlich.

[[ablehnen]]
== Antrag ablehnen

Jede Person mit Rolle Triage kann einen Antrag ablehnen — jederzeit, solange die VM noch
nicht erstellt ist.

=== Empfohlen: Kommando mit Begründung

[source,text]
----
/ablehnen Port 22 darf nicht öffentlich sein. Bitte Zugriff über VPN.
----

*Ereignis:* `issue_comment: created` → Workflow *Kommandos* (Zweig `/ablehnen`)

. *Berechtigung prüfen* — wie bei `/ip`. Ohne Triage: still ignoriert.
. *Bereits abgelehnt?* — 😕 und Hinweis „bereits abgelehnt".
. *Begründung Pflicht* — `/ablehnen` ohne Text: 😕 und Hinweis `/ablehnen <Begründung>`.
  Die Begründung ist alles nach `/ablehnen`, auch mehrzeilig.
. 👍-Reaktion, dann Ablehnung (siehe unten).

=== Rückfall: nur Label `abgelehnt`

Setzt ein Admin nur das Label, läuft der Workflow *Status* (Zweig `abgelehnt`) mit derselben
Ablehnung, aber ohne Begründung. Der Kommentar verweist dann auf „die Begründung in den
Kommentaren oben" — der Admin sollte sie vorher selbst schreiben.

=== Was bei der Ablehnung passiert

. *VM existiert schon* (`status: erstellt`): *nichts wird geschlossen*. Nur Hinweis an die
  Admins: VM zuerst in Proxmox löschen, dann Issue manuell schließen.
. Status-Labels `status: neu` / `status: freigegeben` / `status: ip-vergeben` entfernen,
  Label `abgelehnt` setzen (falls noch nicht gesetzt).
. Kommentar an die Antragsteller*in (DE/EN): „❌ Euer Antrag wurde von @… abgelehnt" +
  Begründung + „Ihr könnt gerne einen neuen, korrigierten Antrag stellen."
. *War die IP schon vergeben* (`status: ip-vergeben`): zusätzlich Erwähnung von
  `IP_VERGABE`, damit die IP wieder freigegeben wird.
. Issue schließen als „not planned" — der Projektname wird wieder frei.

NOTE: Setzt `/ablehnen` das Label `abgelehnt`, löst das den Workflow *Status* nicht erneut aus
(Bot-Änderung mit `GITHUB_TOKEN`). Es gibt also keinen doppelten Kommentar.

[[ohne-workflow]]
== Aktionen ohne Workflow

[cols="2,3",options="header"]
|===
|Aktion |Folge

|Normaler Kommentar (Frage, „brauchen VM nicht mehr")
|Nichts. GitHub benachrichtigt nur Beobachter*innen des Issues und Erwähnte.

|Issue schließen
|Nichts. Der Projektname wird dadurch wieder frei.

|Label manuell entfernen
|Nichts.

|Issue ohne Formular (Blank issue, nur Maintainer)
|Alle Workflows überspringen es (kein Label `vm-antrag`).
|===

[[schutz]]
== Schutzmechanismen

`concurrency` pro Issue::
Laufen zwei Ereignisse gleichzeitig (z.B. zwei schnelle Bearbeitungen), werden sie
nacheinander abgearbeitet.

Minimale Rechte::
Workflows dürfen nur Issues schreiben (`issues: write`) und Code lesen (`contents: read`).

Keine Nutzereingaben in Shell-Befehlen::
Alles läuft in JavaScript über `context.payload`. Eingaben wie `$(rm -rf …)` im Formular
werden nie ausgeführt.

Labels nur für Admins::
Schüler*innen können als Autor*innen keine Labels setzen. Die Status-Kette lässt sich
nicht fälschen.

[[grenzen]]
== Grenzen und offene Punkte

. *Parsing über Überschriften* — Enthält ein Textfeld eine Zeile mit `### …`, wird der Wert
  abgeschnitten. Selten und harmlos.
. *Team nötig* — Ohne Team `vm-admins` (Rolle Triage) können die Admins weder Labels setzen
  noch `/ip` bzw. `/ablehnen` verwenden.

[[test]]
== Testen

Tests nie mit echten Personen — vorher die Variablen auf das eigene Konto setzen, danach
löschen:

[source,bash]
----
gh variable set FREIGABE -R htl-leo-infra/vm-antraege --body htl-leonding
gh variable set VM_ERSTELLUNG -R htl-leo-infra/vm-antraege --body htl-leonding
# … Test-Issues durchspielen …
gh variable delete FREIGABE -R htl-leo-infra/vm-antraege
gh variable delete VM_ERSTELLUNG -R htl-leo-infra/vm-antraege
----
