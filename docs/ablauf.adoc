Technische Beschreibung der GitHub-Actions-Workflows für Admins
(Freigabe, IP-Vergabe, VM-Erstellung), betreuende Lehrkräfte und Betreuer*innen des Repos.

[[grundprinzip]]
== Grundprinzip

GitHub startet bei jedem Ereignis im Repo alle Workflows, die auf dieses Ereignis hören.
Jeder Workflow prüft zuerst eine *Bedingung* (`if:`). Trifft sie nicht zu, wird er sofort
übersprungen („skipped"). Trifft sie zu, lädt er `.github/scripts/antrag.js` und führt ein
Skript aus.

IMPORTANT: Alle Bot-Aktionen (Labels, Kommentare, Titel) laufen mit dem `GITHUB_TOKEN`.
Änderungen mit diesem Token *lösen keine weiteren Workflows aus* — keine Endlosschleifen.
Setzt der Bot z.B. `status: neu`, reagiert kein anderer Workflow darauf.

[cols="2,2,3",options="header"]
|===
|Ereignis |Workflow |Bedingung

|Issue erstellt / bearbeitet
|`antrag-pruefen.yaml` („Antrag prüfen")
|Label `vm-antrag` und Issue offen

|Label hinzugefügt
|`status.yaml` („Status")
|Label `vm-antrag` und Label = `status: av-freigegeben`, `status: erstellt` oder `abgelehnt`

|Kommentar geschrieben
|`kommandos.yaml` („Kommandos")
|beginnt mit `/freigeben`, `/ip`, `/ablehnen` oder `/verlaengern`, Label `vm-antrag`

|täglich 05:17 UTC (oder manuell)
|`ablauf.yaml` („Ablauf")
|alle offenen Issues mit `vm-antrag` und `status: erstellt`
|===

.Status-Kette
[source,text]
----
(Antrag) ──► ungültig ◄──► status: neu ──► status: betreuer-freigegeben ──► status: av-freigegeben ──► status: ip-vergeben ──► status: erstellt
              Bot            Bot            Lehrkraft (/freigeben)           Peter (Label)            Himmelbauer (/ip)        Wagner/Brückner (Label)

Jederzeit vor „erstellt":  /ablehnen <Begründung>  oder Label abgelehnt  ──► abgelehnt + Issue geschlossen
Nach „erstellt":           30 Tage vor Ablauf ──► läuft ab ──► abgelaufen      /verlaengern [Monate] ──► neues Ablaufdatum
----

.Kommandos
[cols="2,2,3",options="header"]
|===
|Kommando |Wer |Wirkung

|`/freigeben` |Lehrkraft, Triage |Freigabe durch die Lehrkraft, nur bei `status: neu` (<<lehrkraft>>)
|`/ip <adresse>` |Triage |IP eintragen, nur bei `status: av-freigegeben` (<<ip>>)
|`/ablehnen <Begründung>` |Lehrkraft, Triage |Antrag ablehnen und schließen (<<ablehnen>>)
|`/verlaengern [Monate]` |Lehrkraft, Triage |Nutzungsdauer verlängern, nur bei `status: erstellt` (<<verlaengern>>)
|===

_Lehrkraft_ = der GitHub-Account im Feld _GitHub-Name der betreuenden Lehrkraft_ (nie die
Antragsteller*in selbst). _Triage_ = Rolle Triage oder höher, d.h. Team `vm-admins`.
Lehrkräfte brauchen keine Rechte im Repo.

[[personen]]
=== Zuständige Personen

Die erwähnten Personen kommen aus Repo-Variablen. Ohne Variable gilt der Default im Workflow.

[cols="1,2,2",options="header"]
|===
|Variable |Aufgabe |Default

|`FREIGABE` |Freigabe durch die Abteilung (AV), nach der Lehrkraft |`bauepete`
|`IP_VERGABE` |IP-Adresse eintragen (Sysadmin Thomas Himmelbauer) |`ghbugfinder`
|`VM_ERSTELLUNG` |VM in Proxmox anlegen („Mailverteiler") |`Master-Andi MWagnerOE5AOO`
|===

[source,bash]
----
gh variable set IP_VERGABE -R htl-leo-infra/vm-antraege --body <username>
----

[[antrag]]
== Schüler*in erstellt den Antrag

*Ereignis:* `issues: opened` → Workflow *Antrag prüfen*

. *Formular auslesen* — Der Issue-Body hat das Format `### Projektname` + Leerzeile + Wert.
  `parseBody()` übersetzt die deutschen bzw. englischen Überschriften in Feld-IDs
  (`projektname`, `internet`, …). `_No response_` gilt als leer.
. *Titel setzen* — `[VM] <projektname>` wird z.B. zu `[VM] notenrechner`.
. *Doppelte Namen suchen* — alle *offenen* Anträge (außer `abgelehnt`) laden und deren
  Projektnamen und DNS-Namen auslesen.
. *Prüfen:*
** *Fehler:* Lehrkraft kein gültiger GitHub-Benutzername, existiert nicht (API-Abfrage) oder
   ist die Antragsteller*in selbst; Teammitglieder leer oder kein gültiger Schul-Benutzername
   (`^(ad|kd|if|it|el|bg)\d{6}$`, z.B. `if123456`); Name ungültig (`^[a-z][a-z0-9-]{2,29}$`) oder bereits vergeben; DNS Name bereits
   von einem anderen offenen Antrag mit Internet „Yes" belegt; bei Internet
   „Yes" fehlen Ports oder DNS; Portnummer ungültig; DNS kein gültiger Hostname
** *Nur Warnung:* Port 22/3306/5432/6379/27017 öffentlich; Ports/DNS angegeben, obwohl
   Internet „No"
. *Mit Fehlern:* Label `ungültig`, Prüfkommentar mit allen Fehlern und unsichtbarer
  Markierung `<!-- vm-antrag:pruefung -->`. Ende — Peter wird *nicht* benachrichtigt.
. *Ohne Fehler:* Label `status: neu`, Kommentar `Neuer VM-Antrag … betreuende Lehrkraft: @<lehrkraft>.
  Bitte … /freigeben` und für die Schüler*innen „Danke, euer Antrag ist eingegangen".
  *GitHub schickt der Lehrkraft eine Mail* (wegen der Erwähnung).

NOTE: Die Sprache richtet sich nach dem Label `english`, das das englische Formular
automatisch setzt. Texte an Schüler*innen sind dann englisch, Texte an Admins immer deutsch.

[[bearbeiten]]
== Schüler*in bearbeitet den Antrag

*Ereignis:* `issues: edited` → derselbe Workflow *Antrag prüfen*, derselbe Ablauf.

* *Immer noch fehlerhaft:* Der *vorhandene* Prüfkommentar wird aktualisiert (erkannt an der
  Markierung) — kein neuer Kommentar.
* *Jetzt korrekt:* Label `ungültig` weg, Prüfkommentar zeigt „✅ gültig". Ist noch kein
  Status-Label gesetzt: `status: neu` und Mail an die Lehrkraft.
* *Lehrkraft geändert, noch bei `status: neu`:* Die neue Lehrkraft wird erwähnt und um
  `/freigeben` gebeten. Die alte Lehrkraft darf nicht mehr freigeben.
* *Bereits freigegeben und nachträglich bearbeitet* (Label `status: betreuer-freigegeben`,
  `status: av-freigegeben`, `status: ip-vergeben` oder `status: erstellt`): Der Bot vergleicht alten und neuen Stand
  (`changes.body.from`) und postet an `FREIGABE` und `VM_ERSTELLUNG` eine Tabelle
  *Feld | vorher | nachher*. Bei geänderten Teammitgliedern zusätzlich
  „*Teammitglieder geändert → Proxmox-Zugriff prüfen!*". Danach wird normal neu geprüft;
  das Status-Label bleibt.

IMPORTANT: Die Teammitglieder (Schul-Benutzernamen) bekommen Zugriff auf die Proxmox-Oberfläche.
Eine Änderung nach der Freigabe muss deshalb immer geprüft werden.

[[lehrkraft]]
== Lehrkraft gibt frei

*Aktion:* Die betreuende Lehrkraft kommentiert `/freigeben`.

*Ereignis:* `issue_comment: created` → Workflow *Kommandos* (Zweig `/freigeben`)

. *Berechtigung prüfen* — Kommentiert die eingetragene Lehrkraft oder jemand mit Triage?
  Sonst still ignoriert. Ein Admin kann so stellvertretend freigeben, wenn die Lehrkraft
  nicht erreichbar ist.
. *Status prüfen* — Nur bei `status: neu` und ohne `ungültig`, sonst 😕 und Hinweis.
. *Erfolg:* Label `status: neu` → `status: betreuer-freigegeben`, 👍-Reaktion, Kommentar
  `@<FREIGABE> Antrag … wurde von @<lehrkraft> (betreuende Lehrkraft) freigegeben. Bitte …
  mit Label status: av-freigegeben freigeben` und für die Schüler*innen „Eure betreuende
  Lehrkraft hat den Antrag freigegeben". *Peter bekommt eine Mail.*

[[freigabe]]
== Peter gibt frei (AV)

*Aktion:* Peter setzt das Label `status: av-freigegeben` (braucht Rolle Triage, d.h. Mitglied
im Team `vm-admins`).

*Ereignis:* `issues: labeled` → Workflow *Status* (Zweig `status: av-freigegeben`)

. *Reihenfolge* — Normalerweise nach der Lehrkraft. Peter darf aber auch direkt bei
  `status: neu` freigeben; der Kommentar vermerkt dann „(ohne Freigabe der Lehrkraft)".
. Labels `status: neu` und `status: betreuer-freigegeben` entfernen.
. Kommentar: `@<IP_VERGABE> Antrag … wurde von @bauepete freigegeben. Bitte /ip 10.x.x.x/24 public x.x.x.x/24`
  und für die Schüler*innen „Euer Antrag wurde freigegeben".
. *Die Person für die IP-Vergabe bekommt eine Mail.*

NOTE: Der Workflow *Status* startet bei jedem Label, läuft aber nur bei `status: av-freigegeben`,
`status: erstellt` und `abgelehnt`. Alle anderen Labels werden übersprungen.

[[ip]]
== Himmelbauer trägt die IP ein

*Aktion:* Kommentar im Issue:

[source,text]
----
/ip 10.9.32.1/24
/ip 10.9.32.1/24 public 193.18.22.7/24
----

Präfix (`/24`) und öffentliche IP sind optional. Statt `public` geht auch `/public`.

*Ereignis:* `issue_comment: created` → Workflow *Kommandos* (Zweig `/ip`)

. *Berechtigung prüfen* — Rolle der kommentierenden Person im Repo abfragen. Unter Triage
  (z.B. Schüler*innen): nur Log-Eintrag, *kein sichtbarer Kommentar*.
. *Status prüfen* — Ohne Label `status: av-freigegeben`: 😕-Reaktion und Hinweis
  „/ip geht nur bei Label status: av-freigegeben".
. *IP prüfen* — Nur die erste Zeile zählt: interne IPv4 mit optionalem Präfix (≤ 32),
  optional `public <IPv4>[/Präfix]`. Sonst 😕 und Formathinweis.
. *Erfolg:*
** Label `status: av-freigegeben` → `status: ip-vergeben`
** 👍-Reaktion auf den Kommentar
** Kommentar `@MWagnerOE5AOO @Master-Andi Bitte VM anlegen …` mit *Tabelle aller Daten*
   und IP, für die Schüler*innen „IP-Adresse eurer VM: …"
** *Michael und Andreas bekommen eine Mail* mit dieser Zusammenfassung — das ist der
   „Mailverteiler".

[[erstellt]]
== VM wird angelegt

*Aktion:* VM in Proxmox anlegen (manuell), danach Label `status: erstellt` setzen.

*Ereignis:* `issues: labeled` → Workflow *Status* (Zweig `status: erstellt`)

. Alle vorherigen Status-Labels entfernen (`status: neu`, `status: betreuer-freigegeben`,
  `status: av-freigegeben`, `status: ip-vergeben`) — auch wenn Schritte übersprungen wurden.
. *Security-Checkliste* (Lynis, Fail2Ban, ClamAV, WAF, SSH-Härtung) an den Issue-Body hängen,
  erkennbar an `<!-- vm-antrag:security -->`. Die Antragsteller*in kann als Autor*in abhaken.
  Wird das Label erneut gesetzt, kommt keine zweite Checkliste.
. *Ablaufdatum* = heute + 12 Monate (bleibt beim erneuten Setzen des Labels gleich).
. Kommentar `@<antragsteller*in> 🎉 Eure VM … ist bereit. Zugangsdaten auf anderem Weg …`
  mit Hinweis auf die Checkliste, Ablaufdatum und unsichtbarem Marker `<!-- ablauf: JJJJ-MM-TT -->`.
. *Die Antragsteller*in bekommt eine Mail.*

WARNING: Zugangsdaten zur VM niemals im Issue posten — das Repo ist öffentlich.

NOTE: Abhaken der Checkliste ist eine Bearbeitung des Issues und startet *Antrag prüfen*.
Die Checkliste ist kein Formularfeld, es gibt also keinen Änderungshinweis an die Admins.

[[verlaengern]]
== Nutzungsdauer und Verlängerung

*Ablaufdatum:* steht als Marker `<!-- ablauf: JJJJ-MM-TT -->` in Bot-Kommentaren. Es gilt
der *letzte* Bot-Kommentar mit Marker. Marker in Kommentaren von Personen werden ignoriert.

=== Täglicher Workflow *Ablauf*

*Ereignis:* `schedule` (täglich 05:17 UTC) oder manuell (`workflow_dispatch`)

Für jedes offene Issue mit `vm-antrag` und `status: erstellt`:

. *Kein Ablaufdatum* (ältere Anträge): Ablaufdatum = heute + 12 Monate nachtragen.
. *Höchstens 30 Tage bis Ablauf:* Label `läuft ab`, Erinnerung an Antragsteller*in und
  Lehrkraft mit Hinweis auf `/verlaengern`. Einmalig (solange das Label gesetzt ist).
. *Ablauftag erreicht:* Label `läuft ab` → `abgelaufen`, Kommentar an Antragsteller*in,
  Lehrkraft und `VM_ERSTELLUNG`: noch benötigt → `/verlaengern`, sonst VM in Proxmox löschen
  und Issue schließen. *Es wird nichts automatisch gelöscht.*

[source,bash]
----
gh workflow run ablauf.yaml -R htl-leo-infra/vm-antraege   # manuell starten
----

=== Kommando `/verlaengern [Monate]`

*Ereignis:* `issue_comment: created` → Workflow *Kommandos* (Zweig `/verlaengern`)

. *Berechtigung* — eingetragene Lehrkraft oder Triage, sonst still ignoriert.
. *Status* — nur bei offenem Issue mit `status: erstellt`.
. *Monate* — 1–12, ohne Angabe 12. Sonst 😕 und Formathinweis.
. *Neues Datum* — ab bisherigem Ablaufdatum, bei bereits abgelaufenen ab heute.
. Labels `läuft ab` und `abgelaufen` entfernen, 👍, Kommentar mit neuem Datum und Marker.

[[ablehnen]]
== Antrag ablehnen

Jede Person mit Rolle Triage und die eingetragene Lehrkraft können einen Antrag ablehnen —
jederzeit, solange die VM noch nicht erstellt ist.

=== Empfohlen: Kommando mit Begründung

[source,text]
----
/ablehnen Port 22 darf nicht öffentlich sein. Bitte Zugriff über VPN.
----

*Ereignis:* `issue_comment: created` → Workflow *Kommandos* (Zweig `/ablehnen`)

. *Berechtigung prüfen* — Triage oder eingetragene Lehrkraft, sonst still ignoriert.
. *Bereits abgelehnt?* — 😕 und Hinweis „bereits abgelehnt".
. *Begründung Pflicht* — `/ablehnen` ohne Text: 😕 und Hinweis `/ablehnen <Begründung>`.
  Die Begründung ist alles nach `/ablehnen`, auch mehrzeilig.
. 👍-Reaktion, dann Ablehnung (siehe unten).

=== Rückfall: nur Label `abgelehnt`

Setzt ein Admin nur das Label, läuft der Workflow *Status* (Zweig `abgelehnt`) mit derselben
Ablehnung, aber ohne Begründung. Der Kommentar verweist dann auf „die Begründung in den
Kommentaren oben" — der Admin sollte sie vorher selbst schreiben.

=== Was bei der Ablehnung passiert

. *VM existiert schon* (`status: erstellt`): *nichts wird geschlossen*. Nur Hinweis an die
  Admins: VM zuerst in Proxmox löschen, dann Issue manuell schließen.
. Status-Labels `status: neu` / `status: betreuer-freigegeben` / `status: av-freigegeben` /
  `status: ip-vergeben` entfernen,
  Label `abgelehnt` setzen (falls noch nicht gesetzt).
. Kommentar an die Antragsteller*in (DE/EN): „❌ Euer Antrag wurde von @… abgelehnt" +
  Begründung + „Ihr könnt gerne einen neuen, korrigierten Antrag stellen."
. *War die IP schon vergeben* (`status: ip-vergeben`): zusätzlich Erwähnung von
  `IP_VERGABE`, damit die IP wieder freigegeben wird.
. Issue schließen als „not planned" — der Projektname wird wieder frei.

NOTE: Setzt `/ablehnen` das Label `abgelehnt`, löst das den Workflow *Status* nicht erneut aus
(Bot-Änderung mit `GITHUB_TOKEN`). Es gibt also keinen doppelten Kommentar.

[[ohne-workflow]]
== Aktionen ohne Workflow

[cols="2,3",options="header"]
|===
|Aktion |Folge

|Normaler Kommentar (Frage, „brauchen VM nicht mehr")
|Nichts. GitHub benachrichtigt nur Beobachter*innen des Issues und Erwähnte.

|Issue schließen
|Nichts. Der Projektname wird dadurch wieder frei.

|Label manuell entfernen
|Nichts.

|Issue ohne Formular (Blank issue, nur Maintainer)
|Alle Workflows überspringen es (kein Label `vm-antrag`).
|===

[[schutz]]
== Schutzmechanismen

`concurrency` pro Issue::
Laufen zwei Ereignisse gleichzeitig (z.B. zwei schnelle Bearbeitungen), werden sie
nacheinander abgearbeitet.

Minimale Rechte::
Workflows dürfen nur Issues schreiben (`issues: write`) und Code lesen (`contents: read`).

Keine Nutzereingaben in Shell-Befehlen::
Alles läuft in JavaScript über `context.payload`. Eingaben wie `$(rm -rf …)` im Formular
werden nie ausgeführt.

Labels nur für Admins::
Schüler*innen können als Autor*innen keine Labels setzen. Die Status-Kette lässt sich
nicht fälschen.

Lehrkraft-Freigabe::
Schüler*innen tragen die Lehrkraft selbst ein. Sich selbst einzutragen wird abgelehnt; ein
anderer Account (z.B. Mitschüler*in) fällt erst bei der AV-Freigabe auf. Deshalb prüft Peter
danach immer noch. Eine Änderung der Lehrkraft nach der Freigabe meldet der Bot an die Admins.

[[grenzen]]
== Grenzen und offene Punkte

. *Parsing über Überschriften* — Enthält ein Textfeld eine Zeile mit `### …`, wird der Wert
  abgeschnitten. Selten und harmlos.
. *Team nötig* — Ohne Team `vm-admins` (Rolle Triage) können die Admins weder Labels setzen
  noch `/ip` bzw. `/ablehnen` verwenden.
. *Zeitplan pausiert* — GitHub deaktiviert `schedule`-Workflows in öffentlichen Repos nach
  60 Tagen ohne Aktivität im Repo. Dann unter _Actions → Ablauf → Enable workflow_ wieder
  einschalten.
. *Alte Anträge* — Anträge mit dem früheren Feld _Betreuende Lehrkraft_ (echter Name) werden
  noch gelesen, wären bei einer Bearbeitung aber `ungültig`.

[[test]]
== Testen

Tests nie mit echten Personen — vorher die Variablen auf das eigene Konto setzen, danach
auf die echten Werte *zurücksetzen*:

[source,bash]
----
R=htl-leo-infra/vm-antraege
for v in FREIGABE IP_VERGABE VM_ERSTELLUNG; do gh variable set $v -R $R --body htl-leonding; done
# … Test-Issues durchspielen …
gh variable set FREIGABE -R $R --body bauepete
gh variable set IP_VERGABE -R $R --body ghbugfinder
gh variable set VM_ERSTELLUNG -R $R --body "Master-Andi MWagnerOE5AOO"
----

WARNING: Variablen nicht löschen — die Defaults in den Workflows weichen ab
(`VM_ERSTELLUNG` in `kommandos.yaml`: andere Reihenfolge).

Lehrkraft-Schritt::
Als Antragsteller*in kann man nicht selbst Lehrkraft sein. Einen zweiten Account ohne
Repo-Rechte eintragen (z.B. `ThomasStuetz`) und `/freigeben`, `/verlaengern`, `/ablehnen`
von dort kommentieren — so wird auch die Berechtigung der Lehrkraft getestet. Notlösung:
`/freigeben` mit Triage (stellvertretend).

Ablauf-Workflow::
`gh workflow run ablauf.yaml -R $R` startet die tägliche Prüfung sofort. Achtung: Erstellte
Anträge ohne Ablaufdatum bekommen dabei eines nachgetragen, mit Erwähnung der
Antragsteller*in. `läuft ab` / `abgelaufen` lassen sich live nur nach entsprechender
Wartezeit testen.
