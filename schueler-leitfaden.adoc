== Was ihr bekommt

Eine virtuelle Maschine (VM) oder einen LXC-Container in der Proxmox-Umgebung der Schule —
für die Dauer eures Projekts. Was darauf läuft, richtet ihr selbst ein.

[cols="1,3",options="header"]
|===
|Typ |Wann?

|*LXC*
|Schlanker Container mit Linux. Reicht für die meisten Web-Anwendungen, Datenbanken und
Docker-Setups. Startet schnell, braucht wenig Ressourcen.

|*VM*
|Vollständige virtuelle Maschine. Nötig, wenn ihr ein anderes Betriebssystem, einen eigenen
Kernel oder Kernel-Module braucht.
|===

TIP: Im Zweifel „Weiß nicht" auswählen und im Feld _Projektbeschreibung_ erklären, was
laufen soll. Wir entscheiden dann mit euch.

== Projektname richtig wählen

Der Projektname wird Teil des VM-Namens. Deshalb gelten strenge Regeln:

* nur Kleinbuchstaben `a`–`z`, Ziffern `0`–`9` und Bindestrich `-`
* keine Leerzeichen, keine Umlaute
* 3 bis 30 Zeichen
* muss mit einem Buchstaben beginnen

[cols="1,1",options="header"]
|===
|✅ Gut |❌ Schlecht

|`notenrechner` |`Notenrechner`
|`leo-mensa` |`leo mensa`
|`da-smarthome` |`Smart_Home_DA`
|===

Ist der Name ungültig, bekommt euer Issue das Label `ungültig` und einen Hinweis. Korrigiert
dann einfach das Issue (Menü `…` → _Edit_), es wird automatisch neu geprüft.

== Teammitglieder: Schul-Benutzernamen

Tragt im Feld _Teammitglieder_ die *Schul-Benutzernamen* aller ein, die am Projekt arbeiten —
einen pro Zeile, klein geschrieben, z.B. `if123456`.

Alle hier eingetragenen Personen bekommen Zugriff auf die *Proxmox-Oberfläche* und können
eure VM schulintern administrieren (starten, stoppen, Konsole).

[cols="1,3",options="header"]
|===
|Kürzel |Abteilung

|`ad` |Abendschule
|`kd` |Kolleg
|`if` |Informatik
|`it` |Medientechnik
|`el` |Elektronik
|`bg` |Biomedizin – Gesundheitstechnik – Medizintechnik
|===

IMPORTANT: Ändert ihr die Teammitglieder nach der Freigabe, werden die Admins automatisch
benachrichtigt und prüfen die Änderung.

== Ausstattung

Wählt so wenig wie möglich — die Ressourcen teilen sich alle Projekte der Schule.

* *CPU-Kerne:* 1–2 reichen für fast alle Schulprojekte.
* *RAM:* 2 GB für eine kleine Web-Anwendung, 4 GB mit Datenbank und Docker.
* *Disk:* 10–20 GB, außer ihr speichert große Datenmengen.

Braucht ihr mehr, wählt „mehr" und begründet es unter _Spezielle Anforderungen_.

== Erreichbarkeit: Internet, Ports und DNS

Standardmäßig ist eure VM *nur im Schulnetz* erreichbar (`Internet: No`).

Soll sie auch aus dem Internet erreichbar sein (`Internet: Yes`), braucht es zusätzlich:

Public Ports::
Welche Ports werden von außen weitergeleitet? Für eine Webseite meist `80, 443`.
*Nur* die Ports angeben, die wirklich öffentlich sein müssen — niemals Datenbank-Ports
(`5432`, `3306`, …) oder SSH (`22`).

DNS Name::
Unter welchem Namen soll die VM erreichbar sein, z.B. `notenrechner.htl-leonding.ac.at`.

[WARNING]
====
Eine VM im Internet wird innerhalb von Minuten von fremden Bots angegriffen. Haltet das
System aktuell, verwendet sichere Passwörter bzw. SSH-Schlüssel und öffnet nur, was nötig ist.
====

=== Absicherung und Überwachung

Zur Absicherung und Überwachung helfen zusätzlich einige bewährte Open-Source-Werkzeuge:

https://cisofy.com/lynis/[Lynis]::
Prüft das System auf Schwachstellen und Konfigurationsfehler und liefert
Verbesserungsvorschläge.

https://www.clamav.net/[ClamAV]::
Erkennt Schadsoftware, etwa in Uploads oder Mail-Anhängen.

https://github.com/fail2ban/fail2ban[Fail2Ban]::
Sperrt IP-Adressen automatisch, wenn sie durch wiederholte fehlgeschlagene Anmeldeversuche
auffallen.

Web Application Firewall::
Für Webserver wie Apache und Nginx empfiehlt sich eine Web Application Firewall (z.B.
https://github.com/owasp-modsecurity/ModSecurity[ModSecurity]) mit den
https://coreruleset.org/[OWASP Core Rule Sets], die gängige Angriffe wie SQL-Injection oder
Cross-Site-Scripting abfangen.

SSH-Härtung::
Schwache SSH-Cipher-Suiten und veraltete Algorithmen deaktivieren, sodass nur moderne, als
sicher geltende Verfahren zugelassen sind.

NOTE: Diese Maßnahmen ersetzen keine regelmäßige Pflege, erhöhen aber den Schutz deutlich.

== Anmeldung für eure Anwendung (Keycloak)

Braucht eure Anwendung eine Anmeldung, baut *keine eigene Benutzerverwaltung* mit
selbst gespeicherten Passwörtern. Die Schule bietet einen sicheren Anmeldedienst (Keycloak):

* *mit Schulkonto:* Nutzer*innen melden sich mit ihrem HTL-Konto an — ihr bekommt Kennung,
  Klasse und Rolle mit.
* *ohne Schulkonto:* auch Zugänge für externe Personen (Eltern, Partnerbetriebe,
  Testpersonen) sind möglich — gebt das im Antrag an.

Den Zugang beantragt ihr separat unter
link:https://github.com/htl-leonding-college/keycloak-antraege[keycloak-antraege]
(Formular „Client für ein Schülerprojekt beantragen").

== Ablauf nach dem Antrag

. Ihr stellt den Antrag — Label `status: neu`.
. Der Antrag wird geprüft und freigegeben — Label `status: freigegeben`.
. Die VM bekommt eine IP-Adresse, sie steht als Kommentar im Issue — Label `status: ip-vergeben`.
. Die VM wird angelegt — Label `status: erstellt`, ihr bekommt eine Nachricht im Issue. Die Zugangsdaten kommen auf einem anderen Weg.

Wird euer Antrag abgelehnt, bekommt ihr die Begründung als Kommentar und das Issue wird
geschlossen (Label `abgelehnt`). Ihr könnt dann einen neuen, korrigierten Antrag stellen.

Fragen stellt ihr als Kommentar direkt in eurem Issue.

== Wenn ihr die VM nicht mehr braucht

Schreibt einen Kommentar in euer Issue. Die VM wird dann gelöscht und das Issue geschlossen.
Spätestens nach der angegebenen _Nutzungsdauer_ wird die VM ohnehin entfernt.

[IMPORTANT]
====
Dieses Repository ist *öffentlich*. Schreibt niemals Passwörter, private Schlüssel oder
Zugangsdaten in ein Issue. Zugangsdaten zur VM bekommt ihr auf einem anderen Weg.
====
