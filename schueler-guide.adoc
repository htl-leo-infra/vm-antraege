== What you get

A virtual machine (VM) or an LXC container in the school's Proxmox environment —
for the duration of your project. You set up whatever runs on it yourselves.

[cols="1,3",options="header"]
|===
|Type |When?

|*LXC*
|Lightweight Linux container. Sufficient for most web applications, databases and
Docker setups. Starts fast, needs few resources.

|*VM*
|Full virtual machine. Needed if you require a different operating system, your own
kernel or kernel modules.
|===

TIP: If unsure, choose "Don't know" and explain in the _Project description_ field what
should run on it. We will decide together with you.

== Choosing the project name

The project name becomes part of the VM name. Therefore strict rules apply:

* only lowercase letters `a`–`z`, digits `0`–`9` and hyphen `-`
* no spaces, no special characters
* 3 to 30 characters
* must start with a letter

[cols="1,1",options="header"]
|===
|✅ Good |❌ Bad

|`gradecalculator` |`GradeCalculator`
|`leo-canteen` |`leo canteen`
|`da-smarthome` |`Smart_Home_DA`
|===

If the name is invalid, your issue gets the label `ungültig` (invalid) and a note. Simply
correct the issue (menu `…` → _Edit_), it will be checked again automatically.

== Team members: school usernames

In the _Team members_ field, enter the *school usernames* of everyone working on the
project — one per line, lowercase, e.g. `if123456`.

Everyone listed here gets access to the *Proxmox web interface* and can administer your VM
within the school network (start, stop, console).

[cols="1,3",options="header"]
|===
|Prefix |Department

|`ad` |Evening school (Abendschule)
|`kd` |College (Kolleg)
|`if` |Computer Science (Informatik)
|`it` |Media Technology (Medientechnik)
|`el` |Electronics (Elektronik)
|`bg` |Biomedical and Health Engineering (Biomedizin – Gesundheitstechnik – Medizintechnik)
|===

IMPORTANT: If you change the team members after approval, the admins are notified
automatically and review the change.

== Resources

Choose as little as possible — all projects of the school share the resources.

* *CPU cores:* 1–2 are enough for almost all school projects.
* *RAM:* 2 GB for a small web application, 4 GB with a database and Docker.
* *Disk:* 10–20 GB, unless you store large amounts of data.

If you need more, choose "more" and justify it under _Special requirements_.

== Reachability: Internet, ports and DNS

By default your VM is reachable *only within the school network* (`Internet: No`).

If it should also be reachable from the internet (`Internet: Yes`), you additionally need:

Public ports::
Which ports are forwarded from outside? For a website usually `80, 443`.
*Only* specify ports that really need to be public — never database ports
(`5432`, `3306`, …) or SSH (`22`).

DNS name::
Under which name the VM should be reachable, e.g. `gradecalculator.htl-leonding.ac.at`.

[WARNING]
====
A VM on the internet is attacked by bots within minutes. Keep the system up to date,
use strong passwords or SSH keys and open only what is necessary. See <<security>>.
====

== Security: tools for basic server protection

[NOTE]
====
Supplement to the PowerPoint slides from the network technology lessons (chapter basic server protection/hardening). This guide does not replace the slides, but shows the practical use of the tools discussed there.
====

=== Installation: LXC container vs. VM

[cols="1,1,1", options="header"]
|===
| |LXC container |VM

|Lynis, Fail2Ban, ClamAV
|*Automatic* – installed when the container is created
|*Manual* – must be set up by the user of the VM
|===

With an LXC container you do not have to install the three basic tools yourself, only configure and use them regularly. With a VM you take care of installation and configuration completely yourself.

=== Lynis – security audit

Checks the system for misconfigurations, outdated software and hardening opportunities.

[source,bash]
----
sudo apt install lynis        # only needed for a VM, already present in LXC
sudo lynis audit system
----

Result: a "Hardening Index" and a list of concrete recommendations. The report is located at `/var/log/lynis.log` or `/var/log/lynis-report.dat`. Run it again regularly (e.g. monthly) and work through the recommendations.

=== ClamAV – virus scanner

Detects malware, e.g. in uploads, mail attachments or shared directories.

[source,bash]
----
sudo apt install clamav clamav-daemon   # only needed for a VM, already present in LXC
sudo freshclam                          # update signatures
sudo clamscan -r /path/to/check         # manual scan, recursive
----

For continuous protection, enable `clamav-daemon` and schedule regular scans, e.g. via cron job.

=== Fail2Ban – protection against brute force

Automatically bans IP addresses after several failed login attempts (SSH, web server logins etc.).

[source,bash]
----
sudo apt install fail2ban       # only needed for a VM, already present in LXC
sudo systemctl enable --now fail2ban
----

Configuration in `/etc/fail2ban/jail.local` (do not edit the original file `jail.conf`). Check the status:

[source,bash]
----
sudo fail2ban-client status
sudo fail2ban-client status sshd
----

=== WAF for Apache and Nginx (OWASP Core Rule Set)

A web application firewall filters attacks such as SQL injection or cross-site scripting before they reach the application. It is based on *ModSecurity* with the *OWASP Core Rule Set (CRS)*.

==== Apache

[source,bash]
----
sudo apt install libapache2-mod-security2
sudo a2enmod security2
sudo cp /etc/modsecurity/modsecurity.conf-recommended /etc/modsecurity/modsecurity.conf
# set SecRuleEngine to "On", download and include the OWASP CRS
sudo systemctl restart apache2
----

==== Nginx

Nginx does not ship with ModSecurity; it needs the ModSecurity-nginx connector module (compiled or via a ready-made distribution package) plus the same OWASP CRS rules.

[IMPORTANT]
====
After setting it up, always test in *detection-only mode* first before switching to "blocking", to rule out false positives in your own application.
====

=== SSH hardening

Disable weak SSH cipher suites and outdated algorithms so that only modern procedures considered secure are allowed.

=== Recommended routine

. Run a Lynis audit, prioritize and work through the recommendations
. Keep ClamAV signatures up to date, schedule regular scans
. Check the Fail2Ban status, adjust jail rules if needed
. Review WAF logs for blocked attacks

For details on the underlying concepts (attack surfaces, hardening, defense in depth) see the PowerPoint slides from the network technology lessons.

NOTE: These measures do not replace regular maintenance, but they increase protection
considerably.

== Login for your application (Keycloak)

If your application needs a login, do *not build your own user management* with
self-stored passwords. The school offers a secure login service (Keycloak):

* *with school account:* users log in with their HTL account — you receive their ID,
  class and role.
* *without school account:* access for external people (parents, partner companies,
  test users) is possible too — state this in the request.

Request access separately at
link:https://github.com/htl-leonding-college/keycloak-antraege[keycloak-antraege]
(form "Client für ein Schülerprojekt beantragen"; the Keycloak guide is in German).

== What happens after the request

The status labels are in German. This is what they mean:

. You submit the request — label `status: neu` (new).
. The request is reviewed and approved — label `status: freigegeben` (approved).
. The VM gets an IP address, it is posted as a comment in the issue — label `status: ip-vergeben` (IP assigned).
. The VM is created — label `status: erstellt` (created), you get a message in the issue. The access credentials come through a separate channel.

If your request is rejected, you get the reason as a comment and the issue is closed
(label `abgelehnt` = rejected). You can then submit a new, corrected request.

Ask questions as a comment directly in your issue — English is fine.

== When you no longer need the VM

Write a comment in your issue. The VM will then be deleted and the issue closed.
At the latest after the specified _Usage period_ the VM will be removed anyway.

[IMPORTANT]
====
This repository is *public*. Never write passwords, private keys or credentials in an
issue. You will receive access credentials for the VM through a different channel.
====
